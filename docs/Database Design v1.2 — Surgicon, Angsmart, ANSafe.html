Rancangan Struktur Database

Ekosistem Surgicon, Angsmart, ANSafe & Landing Page

Versi: 1.2 — Revisi: Guide Checklist (Surgicon) & Shift Reports berantai (Angsmart) Prinsip desain: Master Data Pasien tunggal, normalisasi hingga 3NF pada entitas transaksional, audit trail penuh, JSON dipakai seminimal mungkin (hanya untuk snapshot, bukan sumber kebenaran utama).

Ringkasan perubahan dari v1.1:

  1. Modul Surgicon — ditambahkan guide_checklist_items & patient_guide_checklist_answers, serta kolom baru di patient_guide_logs, untuk mendukung alur: pasien baca guide → isi checklist pemahaman → status COMPLETED otomatis saat semua poin tercentang → hasil diteruskan ke sistem perawat.
  2. Modul Angsmart — tabel handover_logs diganti total menjadi shift_reports dengan kolom previous_report_id (self-referencing) untuk merepresentasikan rantai catatan antar-shift yang berkelanjutan, bukan serah terima formal dua pihak.

1. Asumsi & Keputusan Desain

Beberapa hal di PRD ditulis ringkas (mis. items_checked (JSON)); untuk kebutuhan produksi, JSON tersebut dinormalisasi menjadi tabel master + detail agar bisa diaudit per-item, dicari, dan dilaporkan. Keputusan lain:

  1. Satu tabel users untuk semua staf (perawat Surgicon, perawat ruangan, kepala ruangan, admin/IT), dibedakan lewat role_id. Pasien tidak disimpan di users — punya jalur otentikasi sendiri (No. RM + token/tanggal lahir).
  2. RBAC dimodelkan granular per modul (role_module_access) agar matriks RBAC (Full Akses / Lihat saja / Lihat & isi / —) bisa diatur tanpa ubah kode.
  3. Checklist perawat (Pre-OP & Post-OP) dipecah menjadi tabel master item + transaksi header + detail jawaban, bukan satu kolom JSON. Pola yang sama dipakai ulang untuk checklist pemahaman guide pasien (lihat §3.2).
  4. Asesmen MFS dinormalisasi ke indikator standar Morse Fall Scale (6 indikator baku) agar skor otomatis dihitung dari data terstruktur, bukan dipercaya dari input klien.
  5. nursing_cares dibuat otomatis saat pasien baru ditambahkan (trigger aplikasi/DB).
  6. shift_reports dirancang sebagai rantai catatan (bukan handover formal 2 pihak): setiap laporan baru adalah baris baru yang mereferensikan laporan sebelumnya lewat previous_report_id, sehingga histori "perawat A → B → C → ..." tertelusuri eksplisit, bukan cuma tebakan dari urutan waktu.
  7. Semua tabel transaksi punya created_at; tabel yang butuh audit (checklist, guide log, laporan shift) juga punya kolom yang mengarah ke users.id sebagai penanggung jawab.
  8. Tabel bertanda (Fase 2) tidak wajib ada di rilis MVP tapi disertakan agar skema tidak perlu migrasi besar nanti.

Konvensi penamaan: nama tabel plural, snake_case, PK selalu id, FK selalu <singular_entity>_id (mis. patient_id, nurse_id).

5. Aturan Bisnis yang Mempengaruhi Skema

  1. Auto-provisioning lintas modul: trigger aplikasi pada INSERT patients → otomatis INSERT nursing_cares (status awal AWAITING_ACTION).
  2. Validasi No. RM unik: UNIQUE constraint di patients.medical_record_no, dicek di level DB bukan hanya aplikasi.
  3. Status "Completed" checklist perawat mengunci perubahan fase pasien: semua baris preop_verification_details.is_checked = true untuk preop_verification_id tertentu harus true sebelum status bisa diubah ke COMPLETED.
  4. Guide checklist pasien selesai otomatis: trigger aplikasi mengecek — semua guide_checklist_items.is_active = true untuk guide_type tertentu sudah punya baris patient_guide_checklist_answers.is_checked = true yang berpasangan? Jika ya → patient_guide_logs.checklist_status = 'COMPLETED', checklist_completed_at = NOW(), lalu insert baris ke notifications (type = 'PATIENT_GUIDE_CHECKLIST_COMPLETED') untuk perawat penanggung jawab pasien.
  5. Badge peringatan real-time: dihitung on-the-fly dari patients.surgery_schedule − NOW() < 2 jam DAN patient_guide_logs.is_read = false untuk guide_type = 'PRE_OP'.
  6. Rantai shift report tidak bisa diedit: begitu shift_reports.is_locked = true, baris jadi read-only di level aplikasi (bisa diperkuat trigger BEFORE UPDATE di DB). Perawat shift berikutnya selalu menambah baris baru dengan previous_report_id menunjuk ke laporan terakhir pasien tsb — riwayat lengkap didapat dengan traversal previous_report_id atau cukup ORDER BY recorded_at ASC WHERE patient_id = ?.
  7. Skor MFS dihitung server-side dari SUM(mfs_indicator_options.score) di mfs_assessment_details, disimpan sebagai cache di mfs_assessments.total_score agar query dashboard cepat, tapi tetap bisa direkalkulasi ulang untuk audit.
